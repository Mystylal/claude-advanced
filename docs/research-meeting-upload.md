# Research: технологическая реализация загрузки и хранения файлов встречи

**Контекст**: @docs/plan-meeting-file-upload-and-storage.md, @docs/prd-meeting-file-upload-and-storage.md
**Дата**: 2026-08-01

Цель документа — зафиксировать конкретные технические решения (библиотеки, паттерны, ограничения) для Фазы 1–2 (`apps/api`) и Фазы 3 (`apps/web`) плана, до начала реализации.

## 1. Стек загрузки на бэкенде

`apps/api` — NestJS 11 на `@nestjs/platform-express` (Express, не Fastify). Стандартный путь для `multipart/form-data` в Nest на Express — `FileInterceptor`/`FilesInterceptor` из `@nestjs/platform-express`, которые оборачивают **multer**.

Проверено локально: multer уже присутствует в дереве зависимостей транзитивно (через `@nestjs/platform-express`, `node_modules/multer@2.2.0`), но не объявлен как прямая зависимость `apps/api/package.json` — стоит добавить `multer` и `@types/multer` явно, раз код будет напрямую импортировать `diskStorage`/типы из него (transitive-only зависимость может обновиться независимо и сломать сборку).

### 1.1 Почему multer, а не ручной busboy-парсинг

Рассматривались два варианта:

1. **`FileInterceptor` + `multer.diskStorage`** — декларативно, стандартно для Nest/Express, поддерживает лимиты и фильтрацию "из коробки".
2. **Ручной multipart-парсинг через `busboy`** (multer сам построен поверх него) — даёт больше контроля над потоком (например, можно прервать чтение стрима до записи на диск при провале валидации на середине файла), но требует писать свой Nest-интерсептор/guard и дублировать то, что multer уже делает.

**Решение: вариант 1 (multer + `diskStorage`).** Причины:

- PRD/план требуют потоковой записи без буферизации файла целиком в памяти. `multer.diskStorage` пишет каждый файл через `fs.createWriteStream` по мере поступления чанков multipart-стрима — файл никогда не оказывается целиком в памяти процесса. Это выполняется независимо от способа парсинга (busboy или multer), поэтому ручной busboy не даёт здесь выигрыша, только больше кода.
- `MemoryStorage` (`multer.memoryStorage()`) — единственный вариант multer, который буферизует в памяти; его использовать нельзя (нарушает ограничение из PRD п. "Технические ограничения"). Явно зафиксировать в реализации `storage: diskStorage(...)`, не default (default multer storage — тоже disk, но лучше указать явно и с контролем пути).
- Ограничения по размеру (`limits.fileSize`) в multer проверяются потоково — multer обрывает запись и удаляет частично записанный файл, если лимит превышен, не дожидаясь докачки всего файла. Это соответствует требованию "отклонять несоответствующие файлы с понятной ошибкой" без траты диска/памяти на заведомо невалидные файлы.

### 1.2 Пример интерсептора

```ts
@Post(':id/files')
@UseInterceptors(
  FileInterceptor('file', {
    storage: diskStorage({
      destination: (req, file, cb) => {
        const dir = join(storageRoot, req.params.id);
        fs.mkdirSync(dir, { recursive: true });
        cb(null, dir);
      },
      filename: (req, file, cb) => {
        cb(null, `${randomUUID()}${extname(file.originalname)}`);
      },
    }),
    limits: { fileSize: MAX_FILE_SIZE_BYTES },
    fileFilter: (req, file, cb) => {
      cb(null, ALLOWED_MIME_TYPES.has(file.mimetype));
    },
  }),
)
async uploadFile(
  @Param('id') meetingId: string,
  @UploadedFile() file: Express.Multer.File,
  @Req() req: AuthenticatedRequest,
) { ... }
```

`destination`/`filename` — генерация пути в момент, когда заголовки multipart-части уже разобраны, но до начала записи тела файла: это тот самый "потоковый" путь без промежуточного буфера.

### 1.3 Валидация MIME-типа: ограничение и как его закрыть

`file.mimetype` в multer берётся из `Content-Type` заголовка конкретной части multipart-запроса — это **клиентское заявление**, не проверка содержимого (легко подделать, переименовав файл и выставив нужный заголовок). Для PRD это допустимо как базовый уровень (антивирус/модерация содержимого явно **вне скоупа**), но заявленный mime-тип — не гарантия реального формата файла.

Более строгий вариант — досигнатурная проверка "magic bytes" через пакет `file-type` (уже транзитивно есть в дереве зависимостей, но не объявлен явно) поверх уже сохранённого на диск файла (читается только первые ~4100 байт, не весь файл): после того как multer дописал файл, дополнительно вызвать `fileTypeFromFile(path)` и сверить с ожидаемым mime; при несовпадении — удалить файл и вернуть 4xx. Это чуть усложняет happy path (двухфазная проверка: multer `fileFilter` по заголовку → пост-проверка по содержимому), но точнее соответствует "допустимые mime-типы" из PRD, чем доверие одному лишь заголовку.

**Рекомендация**: на Фазу 2 в плане заложить только проверку по заголовку `Content-Type` (`fileFilter`) — это соответствует формулировке плана ("отклонять несоответствующие файлы") и не требует новой прямой зависимости. Проверку по сигнатуре файла (`file-type`) стоит явно вынести как последующее улучшение (или отдельный пункт, если заказчик хочет более строгую защиту), а не молча добавлять в Фазу 2 — влияет на объём задачи.

### 1.4 Конкретные лимиты (нужно зафиксировать в реализации Фазы 2)

План требует "определить и зафиксировать" лимит и типы. Предложение, отталкиваясь от характера файлов встречи (аудио/видео/документы):

- **Максимальный размер**: 512 МБ на файл. Достаточно для типичной аудиозаписи встречи (десятки-сотни МБ) и большинства документов; видеозаписи длинных встреч могут быть больше — если ожидается такое, лимит стоит обсудить с продуктом отдельно, т.к. это упирается в свободное место на диске сервера API (никакого внешнего объектного хранилища в скоупе нет).
- **Допустимые MIME-типы**:
  - Аудио: `audio/mpeg`, `audio/wav`, `audio/x-wav`, `audio/mp4`, `audio/webm`
  - Видео: `video/mp4`, `video/webm`, `video/quicktime`
  - Документы: `application/pdf`, `text/plain`, `application/msword`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`
- Оба списка/константы держать в одном месте модуля файлов (например, `src/meeting-files/constants.ts`), а не разбрасывать магические строки — понадобятся и в `fileFilter` (backend), и в тексте ошибки для фронтенда.

Финальные цифры — решение продукта/плана, не чисто техническое; здесь фиксируется, что для этого нужно и почему выбраны такие категории.

## 2. Структура хранения на диске

- Корень: отдельная директория внутри `apps/api`, например `apps/api/storage/meeting-files/`, **не** внутри `src/` (чтобы не попадать в компиляцию Nest CLI и не путаться с исходниками).
- Путь на файл: `storage/meeting-files/<meetingId>/<uuid>.<ext>` — папка на встречу упрощает "удалить все файлы встречи" (в этой итерации не требуется, но естественно ложится на файловую структуру) и исключает коллизии имён между встречами.
- Хранить **сгенерированный** uuid-based filename на диске, а не оригинальное имя файла — оригинальное имя (`originalName`) хранится только в БД для отображения. Это убирает целый класс проблем: path traversal через имя файла (`../../etc/passwd`), не-ASCII/специальные символы в имени, коллизии при одинаковых именах у разных загрузок.
- `.gitignore` (root или `apps/api/.gitignore`): добавить `apps/api/storage/` (по аналогии с тем, как в проекте уже исключены `.env`/`node_modules`) — файл-плейсхолдер `.gitkeep` в самой директории, если нужно, чтобы папка существовала в чистом чекауте (или создавать её лениво в `destination` callback, как в примере выше — тогда `.gitkeep` не обязателен).
- Путь, сохраняемый в БД (`storagePath`), — **относительный** от `storage/meeting-files/`, не абсолютный путь на диске: делает данные переносимыми между окружениями (dev-машина, CI, сервер) и не течёт абсолютный FS-путь наружу через API-ответы, если DTO по ошибке отдаст поле как есть.

## 3. Модель данных (Prisma)

По аналогии с `Meeting` (`prisma/schema.prisma`):

```prisma
enum MeetingFileStatus {
  pending
  processed
}

model MeetingFile {
  id          String            @id @default(uuid())
  meeting     Meeting           @relation(fields: [meetingId], references: [id])
  meetingId   String
  fileName    String            // оригинальное имя, для отображения
  mimeType    String
  size        Int               // байты
  storagePath String            // относительный путь в storage/meeting-files/
  status      MeetingFileStatus @default(pending)
  uploadedBy  String            // FK на User, аналогично ownerId у Meeting
  uploader    User              @relation(fields: [uploadedBy], references: [id])
  createdAt   DateTime          @default(now())
}
```

Заметки:

- `status` как enum, а не строку — Prisma enum даёт валидацию на уровне БД и явную точку расширения ("future processing status" из плана), без риска опечатки в строковом значении.
- `size` как `Int` (Postgres `integer`, до ~2.1 ГБ) — с лимитом файла 512 МБ укладывается с запасом; если лимит вырастет выше ~2 ГБ в будущем, потребуется `BigInt`.
- `uploadedBy` отдельно от `Meeting.ownerId` — план явно требует различать "кто загрузил" (любой участник) и "кто владелец встречи" (может удалить любой файл); это две разные сущности, обе нужны в записи файла.
- Нужна миграция (`npx prisma migrate dev`) и добавление обратной связи `files MeetingFile[]` в модель `Meeting` и `User` (аналогично `meetings Meeting[]` у `User`).

## 4. Модуль и контроль доступа (CQRS)

PRD прямо требует отдельный CQRS-модуль `meeting-files`, обращающийся к `MeetingsModule` только через `CommandBus`/`QueryBus` — так же, как `AuthModule` обращается к `UsersModule` (см. `apps/api/CLAUDE.md`, раздел про `src/auth/`).

Практическая реализация проверки доступа:

- Переиспользовать существующий `GetMeetingQuery` (`src/meetings/queries/impl/get-meeting.query.ts`) — он уже скоупит по `ownerId` текущего пользователя и кидает 404. Но текущая реализация (`queries/handlers/get-meeting.handler.ts`) сделана "встреча видна только владельцу" — для файлов встречи нужен доступ ещё и для `participants` (не только владельца). Это значит: **либо** расширить `GetMeetingQuery`/его хендлер, чтобы отдавать встречу, если пользователь — владелец **или** есть в `participants`, **либо** завести отдельный query (`GetMeetingForParticipantQuery`) специально под этот кейс, чтобы не менять поведение существующего эндпоинта `GET /meetings/:id`, которым, возможно, осознанно ограничен только владелец.
  - Это расхождение стоит явно решить в начале Фазы 1 (до e2e-теста), т.к. от него зависит, какой query будет дёргать модуль файлов через `QueryBus`. Рекомендация: **не трогать** существующий `GetMeetingQuery` (у него, вероятно, обоснованно урезанный скоуп "мои встречи" для списка/карточки), завести отдельный query в `MeetingsModule` для "имею ли я как участник доступ к этой встрече", возвращающий встречу+флаг роли (owner/participant) или 403/404.
- Различие owner vs participant нужно в каждом хендлере файлов:
  - upload/list/download — owner **или** participant (email в массиве `participants`, как указано в "Технических ограничениях" PRD — `request.user.email`, не `userId`, т.к. `participants` хранит email-строки).
  - delete — только owner (`request.user.userId === meeting.ownerId`), независимо от `uploadedBy`.
- Guard уровня класса: аналогично `MeetingsController`, вешать `JwtAuthGuard` на контроллер файлов, доступ к конкретной встрече проверять внутри хендлера (через `QueryBus`), не отдельным guard'ом — так же, как сейчас устроено в `MeetingsController`.

## 5. Скачивание файла

Nest даёт готовый примитив для потокового ответа: `StreamableFile` (`@nestjs/common`), обёртка над `fs.createReadStream`, которая пишет чанки в HTTP-ответ по мере чтения — симметрично загрузке, без буферизации всего файла в памяти на отдаче.

```ts
@Get(':id/files/:fileId')
async downloadFile(...): Promise<StreamableFile> {
  const meetingFile = await this.queryBus.execute(new GetMeetingFileQuery(...));
  const stream = fs.createReadStream(resolveStoragePath(meetingFile.storagePath));
  return new StreamableFile(stream, {
    type: meetingFile.mimeType,
    disposition: `attachment; filename="${encodeURIComponent(meetingFile.fileName)}"`,
  });
}
```

`encodeURIComponent` на имени файла в `Content-Disposition` — важно, если оригинальное имя содержит не-ASCII символы (кириллица в названии файла — вполне вероятный кейс для этого продукта); голый `filename="..."` с не-ASCII ломается в части браузеров/HTTP-клиентов, стоит сразу использовать RFC 5987 форму (`filename*=UTF-8''...`) либо совместимый вариант через `encodeURIComponent`.

## 6. Удаление файла

Два шага, оба должны быть согласованы:

1. Удалить запись в БД (`prisma.meetingFile.delete`).
2. Удалить файл с диска (`fs.promises.unlink`).

Порядок и обработка ошибок:

- Удалять из БД **после** успешного удаления с диска, либо в обратном порядке с учётом идемпотентности — важно не оставить "осиротевшую" запись в БД, указывающую на уже не существующий файл (хуже для UX — файл виден в списке, но скачивание 404/500), чем на диске повисший файл без записи (просто занимает место, не ломает UX). Рекомендация: сначала `unlink`, если файл не найден на диске (`ENOENT`) — не считать это фатальной ошибкой (в конце концов запись всё равно надо убрать), залогировать предупреждение и продолжить удаление записи в БД. Так система не застревает в противоречивом состоянии из-за рассинхрона диск/БД.
- Не оборачивать в Prisma-транзакцию с файловой операцией — файловая система не участвует в транзакциях БД; при частичном сбое (файл удалён, БД-запрос упал) корректный подход — ретраить/логировать, а не пытаться атомарно связать два разнородных ресурса.

## 7. Тестирование (e2e, `apps/api`)

`supertest` (уже используется в `test/auth.e2e-spec.ts`, `test/meetings.e2e-spec.ts`) поддерживает multipart через `.attach(field, buffer | path, filename)`:

```ts
await request(app.getHttpServer())
  .post(`/meetings/${meetingId}/files`)
  .set("Authorization", `Bearer ${token}`)
  .attach("file", Buffer.from("fake audio content"), "recording.mp3")
  .expect(201);
```

Для теста лимита размера — сгенерировать `Buffer.alloc(MAX_FILE_SIZE_BYTES + 1)` в памяти теста (это тестовый код, не продовый путь — ограничение "не буферизовать" относится к серверной реализации, а не к тестовому клиенту) и ожидать 4xx. Для теста недопустимого mime — `.attach('file', buffer, { filename: 'virus.exe', contentType: 'application/x-msdownload' })` (supertest/form-data позволяет явно задать `contentType` независимо от расширения).

Тестовые файлы, реально записанные на диск в ходе e2e, стоит удалять в `afterAll`/`afterEach` теста (или указывать тестовый storage-root, отдельный от dev-данных, например `storage/meeting-files-test/`, чистящийся между прогонами) — иначе `npm run test:e2e:api`, гоняемый в pre-commit хуке (см. root `CLAUDE.md`), будет постепенно засорять диск разработчика.

## 8. Фронтенд (Фаза 3, `apps/web`)

- **Запрос**: `fetch` с `FormData` не даёт события прогресса загрузки (`fetch` не эмитит upload-progress событий в стабильной кросс-браузерной форме). В проекте нет `axios` (см. `apps/web/package.json`) — добавлять его только ради прогресса избыточно. Рекомендация: для этого конкретного вызова использовать `XMLHttpRequest` напрямую (`xhr.upload.onprogress`), обернув в небольшую промис-функцию рядом с существующим `src/lib/api.ts` (тонкая обёртка, не подменяющая `fetch` для остальных вызовов — только для upload, единственного места, где нужен прогресс).
- Существующий `src/lib/api.ts` уже нормализует ошибки Nest (`ApiError`, `message: string | string[]`) — ошибки 4xx от `fileFilter`/лимита размера (413/400) должны попасть в тот же паттерн, чтобы форма загрузки могла показать текст ошибки без специального парсинга.
- Список файлов (имя/тип/размер/дата/кто загрузил) — обычный `GET`, добавить `getMeetingFiles(meetingId)` в `src/lib/api.ts` рядом с `getMeetings`, тем же паттерном (bearer-токен из `src/lib/auth.ts`).
- Скачивание — обычная ссылка `<a href="${apiUrl}/meetings/:id/files/:fileId" />` с токеном возникает проблема: `<a>` не может проставить `Authorization` заголовок. Два варианта:
  1. Авторизация файловых эндпоинтов через query-параметр токена в дополнение к заголовку (типичный паттерн для download-ссылок) — расширяет `JwtAuthGuard`, чтобы читать токен из `req.query.token`, если заголовка нет.
  2. Скачивание через `fetch` с заголовком + получение `Blob` + программный `URL.createObjectURL` + синтетический клик по `<a>` — не меняет бэкенд, но чуть больше кода на фронте и держит весь файл в памяти вкладки браузера (для больших видео это может быть некомфортно, хотя и не блокирует, в отличие от серверной буферизации).
  - Рекомендация: вариант 2 (без изменений в guard) — проще с точки зрения безопасности (не плодит второй канал передачи токена через URL, который может уйти в логи прокси/браузера), а объём файлов на скачивание через UI (не программный API-клиент) на практике ограничен тем, что пользователь готов ждать в браузере.
- Индикация ошибок лимита/типа — текст ошибки с бэкенда (см. `ApiError`) должен явно называть проблему ("файл превышает 512 МБ" / "неподдерживаемый тип файла: image/svg+xml"), а не generic "upload failed" — иначе фронтенду нечего показать пользователю осмысленного, а PRD явно требует "отображение ошибки загрузки (включая ошибки лимита размера/недопустимого типа от бэкенда)".
- Как и остальной `apps/web`, верификация — через Playwright MCP на живом dev-сервере (не поднимать сервер самостоятельно, см. `apps/web/CLAUDE.md`) + `ui-ux-pro-max` skill, согласно уже описанному в плане чек-листу.

| Парсинг multipart        | `@nestjs/platform-express` `FileInterceptor` (multer), не ручной busboy                                                                        |
| Хранилище multer         | `diskStorage`, явно не `memoryStorage`                                                                                                         |
| Имя файла на диске       | `uuid + расширение`, оригинальное имя только в БД                                                                                              |
| Путь хранения            | `apps/api/storage/meeting-files/<meetingId>/<uuid>.<ext>`, в `.gitignore`                                                                      |
| Валидация типа (Фаза 2)  | По `Content-Type` (multer `fileFilter`); проверка по сигнатуре файла (`file-type`) — отдельное последующее улучшение, не молча в скоупе Фазы 2 |
| Лимит размера            | Предложение: 512 МБ, требует подтверждения продукта                                                                                            |
| Доступ owner/participant | Новый query в `MeetingsModule` (не расширять существующий `GetMeetingQuery`), диспатчится модулем файлов через `QueryBus`                      |
| Отдача файла             | `StreamableFile` + `fs.createReadStream`, `Content-Disposition` с `encodeURIComponent` для не-ASCII имён                                       |
| Удаление                 | `unlink` → (толерантно к `ENOENT`) → удаление записи из БД, без транзакции                                                                     |
| e2e-тесты                | `supertest .attach()`, отдельный/чистящийся storage-root для тестов                                                                            |
| Фронтенд upload-прогресс | `XMLHttpRequest` точечно для одного вызова, без добавления `axios` в проект                                                                    |
| Фронтенд скачивание      | `fetch` + `Blob` + `URL.createObjectURL`, без токена в query-параметре                                                                         |

## 10. Открытые вопросы к продукту/плану

1. Точные значения лимита размера файла и список mime-типов (раздел 1.4) — предложение есть, но финальное число/список нужно подтвердить.
2. Скоуп доступа `GetMeetingQuery` (раздел 4) — расширять существующий query или заводить отдельный: затрагивает `MeetingsModule`, стоит решить явно, а не по ходу реализации Фазы 1.
3. Проверка mime по содержимому файла (`file-type`, раздел 1.3) — включать в скоуп Фазы 2 или оставить как будущее улучшение.
