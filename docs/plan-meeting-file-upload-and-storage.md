# Plan: Meeting file upload and storage

**PRD**: @docs/prd-meeting-file-upload-and-storage.md
**Дата**: 2026-08-01

## Фазы реализации

### Фаза 1: Backend — минимальный путь загрузки и списка файлов (Tracer Bullet)

**Цель:** Участник встречи может загрузить файл через API и увидеть его в списке файлов встречи.
**Затрагивает:** backend, database
**Задачи:**

- [ ] Написать e2e-тест (`test/*.e2e-spec.ts`) на загрузку файла и получение списка файлов встречи, включая проверку 403/404 для пользователя, не являющегося участником встречи — ожидаемо красный на старте фазы.
- [ ] Добавить в `prisma/schema.prisma` модель файла встречи (имя, mime-тип, размер, путь хранения, кто загрузил, дата загрузки, поле статуса обработки вроде `pending`/`processed`), связанную с `Meeting`.
- [ ] Создать отдельный CQRS-модуль файлов встреч (по аналогии с `src/meetings/`), взаимодействующий с `MeetingsModule` через `CommandBus`/`QueryBus`.
- [ ] Реализовать `POST /meetings/:id/files` (стриминговая загрузка на локальную ФС, без буферизации целиком в памяти) и `GET /meetings/:id/files`, с проверкой доступа (`request.user.email` в `ownerId`/`participants`).
- [ ] Прогнать `npm run test:e2e:api` и убедиться, что тест из п.1 стал зелёным.

**Когда готова:** e2e-тест на загрузку и список файлов встречи, написанный в начале фазы, проходит зелёным; попытка постороннего пользователя получает 403/404.

### Фаза 2: Backend — скачивание, удаление и ограничения на файлы

**Цель:** Полный набор операций с файлами встречи на бэкенде, включая контроль доступа и лимиты.
**Затрагивает:** backend
**Задачи:**

- [ ] Написать e2e-тесты на скачивание файла, на удаление файла владельцем (своего и чужого), на отказ в удалении не-владельцу (403) и на отклонение загрузки файла вне лимита размера/типа — ожидаемо красные на старте фазы.
- [ ] Реализовать `GET /meetings/:id/files/:fileId` — скачивание файла (владелец и participants встречи).
- [ ] Реализовать `DELETE /meetings/:id/files/:fileId` — удаление файла (только владелец встречи, независимо от того, кто загрузил), с удалением записи из БД и файла из хранилища.
- [ ] Определить и зафиксировать лимит размера файла и список допустимых mime-типов (аудио, видео, документы); отклонять несоответствующие файлы с понятной ошибкой. Исключить директорию хранения файлов из системы контроля версий (`.gitignore`).
- [ ] Прогнать `npm run test:e2e:api` и убедиться, что все тесты из п.1 стали зелёными.

**Когда готова:** e2e-тесты на скачивание, удаление и лимиты, написанные в начале фазы, проходят зелёными; все четыре эндпоинта (upload/list/download/delete) корректно разграничивают доступ владелец/участник/посторонний.

### Фаза 3: Frontend — блок "Файлы встречи"

**Цель:** Участник встречи видит и может загружать/скачивать/удалять файлы прямо со страницы встречи.
**Затрагивает:** frontend
**Задачи:**

- [ ] Добавить блок "Файлы встречи" на странице встречи со списком прикреплённых файлов (имя, тип, размер, дата загрузки, кто загрузил).
- [ ] Добавить элемент загрузки файла: выбор файла, индикация процесса загрузки, отображение ошибки загрузки (включая ошибки лимита размера/недопустимого типа от бэкенда).
- [ ] Добавить возможность скачать файл из блока для всех участников встречи; показывать действие удаления только владельцу встречи.
- [ ] Проверить блок через Playwright MCP на запущенном dev-сервере (загрузка, список, скачивание, удаление, отображение ошибки) и через `ui-ux-pro-max`, как того требует `apps/web/CLAUDE.md` — автоматического e2e-фреймворка на фронтенде нет, поэтому "красное" состояние здесь не формализуется тестом, а фиксируется чек-листом сценариев из PRD перед версткой.

**Когда готова:** На странице встречи виден список файлов с нужными полями, файл можно загрузить с индикацией прогресса и ошибок, скачать могут все участники, удаление видно и работает только у владельца — все сценарии подтверждены визуальной проверкой через Playwright MCP.

## Примечание про тесты

Для `apps/api` тест пишется в начале фазы (ожидаемо красный, т.к. функциональности ещё нет) и фаза считается завершённой, когда написанный тест становится зелёным. Для `apps/web` автоматических e2e-тестов в проекте пока нет (см. `apps/web/CLAUDE.md`), поэтому фаза 3 верифицируется вручную через Playwright MCP по тому же принципу «сценарий описан заранее → подтверждён после реализации».
